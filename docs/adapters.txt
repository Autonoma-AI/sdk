# Adapters

The Autonoma SDK uses two types of adapters: ORM adapters and server adapters. Each adapter is a separate package in the language's ecosystem. This page describes what each adapter must do, independent of any specific language or ORM.

## ORM Adapter

An ORM adapter connects the SDK core to your database through your ORM. It implements three operations and exposes a name property.

### name

A string identifying the ORM (e.g., "prisma", "drizzle", "sqlalchemy", "ecto"). The SDK includes this in the sdk metadata field of every response, so the platform knows which ORM is in use.

### getSchema

Read the ORM's metadata and return a standardized schema description. This tells the SDK everything about your database: models, fields, FK edges, and named relations.

What it must return:
- A list of models, each with its fields (name, type, whether required, whether it's a primary key, whether it has a default value)
- A list of FK edges (which model holds the FK, which model it points to, the local column name, the foreign column name, whether the FK is nullable)
- A list of named relations (parent model, child model, relation field name on the parent, FK column name on the child)
- The scope field name

Important details:
- Auto-updated timestamp fields should be marked as having a default, so they are not required in scenarios.
- Auto-generated fields (UUIDs, auto-increment) should be marked as having a default.
- The relation field name (the name used for nesting in scenarios) must match the exact name from the ORM schema. This is what users write in scenario JSON keys.
- Cache the result -- getSchema is called on every request.

### createEntities

Create records in the database from a resolved specification. The SDK calls this once per model group, after all FK values have been set.

The specification for each model includes:
- A count of how many records to create
- An array of field objects (one per record), with all values already resolved
- A batch flag indicating whether to use bulk insert

Implementation rules:
- If batch is true: use the ORM's bulk insert method (e.g., createMany, insert_all, Repo.insert_all). Return an empty collection, since bulk insert typically does not return individual records.
- If batch is false: create each record individually. Return all created records with their IDs, since subsequent operations may reference them.
- Wrap everything in a transaction for atomicity.
- The model name in the specification is PascalCase. Convert to whatever case your ORM expects.

### teardown

Delete all data created during a test run. The SDK provides both the scope value (the root entity's ID) and the full set of created record references.

Implementation rules:
1. Get the FK graph from getSchema.
2. Break circular FKs first: if the graph has cycles, find a nullable FK in the cycle and set it to null before deleting.
3. Delete scoped models: for each model that has the scope FK, delete all records where the scope field equals the scope value. Do this in reverse topological order (children before parents) to avoid FK constraint violations.
4. Delete non-scoped models by ID: some models (like User in a join-table setup) may not have the scope FK directly. Delete them by their individual IDs from the refs.
5. Delete the scope root entity last.

The SDK core provides graph utilities (topological sort, cycle detection, deferrable edge finding) that adapters should use for ordering.

### updateEntity (optional)

Update a single record by ID. This is needed for circular FK resolution: when two models reference each other, one must be created with a null FK and then updated after the other is created.

If not implemented and the schema has circular FKs, the SDK will raise an error asking for this method.

## Server Adapter

A server adapter converts between your HTTP framework's request/response types and the SDK's internal format. It is typically very small -- around 15-20 lines of code.

### What it must do

1. Extract the raw request body as a string. This is critical -- the HMAC signature is computed over the exact bytes of the body. The adapter must get the body before any JSON parsing or middleware transformation.

2. Extract request headers as a flat key-value map with lowercase keys.

3. Call the SDK core's handleRequest function with the configuration and the extracted body + headers.

4. Write the returned status code and JSON body to the framework's response.

### Framework-specific considerations

Web standard frameworks (Next.js App Router, Hono, Bun, Deno): read the body with req.text(), iterate headers with req.headers.forEach().

Express: if body-parsing middleware is active, the body may already be parsed. Either configure the route to receive the raw body as a string, or re-serialize it (less ideal, since it may not match the original bytes exactly).

Node.js http: collect chunks from the request stream into a buffer, then convert to string.

Phoenix/Plug (Elixir): use a custom body reader or Plug.Parsers configuration to preserve the raw body alongside the parsed version.

ASGI/WSGI (Python): read the raw body from the request object before any framework-level parsing.

### The name property

Server adapters also expose a name (e.g., "web", "express", "phoenix", "fastapi") that the SDK includes in response metadata.

## Language-specific adapter packages

Each language has its own set of adapter packages. Refer to the language-specific documentation for package names, installation instructions, and code examples:

- TypeScript: sdks/typescript/docs/
- Python: sdks/python/docs/
- Elixir: sdks/elixir/docs/

The protocol behavior is identical across all languages. Only the package names, syntax, and ORM-specific details differ.
