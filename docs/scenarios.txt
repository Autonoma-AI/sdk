# Writing Scenario Data

Scenario data describes what database records to create. The Autonoma platform generates this from your schema, but you may write it for integration tests and debugging.

## Why not raw SQL?

The Environment Factory is designed with hard constraints that make it safe by construction:

1. EXPLICIT OPT-IN
   The endpoint returns 404 unless allowProduction is set to true. The SDK does not inspect the environment (NODE_ENV, etc.) — this explicit flag is the only switch.

2. UP CAN ONLY CREATE
   The up action calls ORM create methods. It cannot UPDATE, DELETE, DROP, TRUNCATE, or run raw SQL. The worst it can do is INSERT rows.

3. DOWN CAN ONLY DELETE WHAT UP CREATED
   During up, the SDK signs a token with the IDs of every created record, using your signing secret (not the shared secret). During down, the SDK verifies that token before deleting. It deletes only the records listed in the token. Even Autonoma cannot forge or modify this token.

4. REQUESTS ARE AUTHENTICATED
   Every request is HMAC-SHA256 signed with the shared secret. Unsigned or tampered requests are rejected with 401.

5. NO RAW SQL
   All database operations go through your ORM. The SDK uses ORM create and delete methods, not SQL strings. Schema validation happens at the ORM level.

Contrast with raw SQL: a raw SQL endpoint could DROP TABLE, DELETE FROM users, or UPDATE users SET role = 'admin'. Even with auth, one malformed query could destroy production data. The Environment Factory can't do any of that.

This is why scenario data is a structured JSON object, not SQL. The SDK interprets it as a series of factory create calls -- nothing more.

## The format

Data is a FLAT map. The top-level keys are model names from your database schema; each value is an array of records to create for that model. A model is created ONLY when it appears as a top-level key. There is NO nesting -- you do not place one model's records inside another model's fields. (If you do, the SDK treats that array as opaque field data and passes it to the factory verbatim; it is NOT created as separate records.)

Every cross-model link is expressed with `_alias`/`_ref`: name a record with `_alias`, and point a foreign key at it with `{ "_ref": "alias" }`. The SDK topologically sorts the records from this `_alias`/`_ref` graph, so the order of keys does not matter. There is no relation introspection — dependency order comes entirely from the `_ref` edges you write.

All field values must be complete and literal -- the SDK does not perform any template resolution or variable substitution. The platform is responsible for generating fully resolved data before sending it.

### Minimal example (org + user)

  {
    "create": {
      "Organization": [{ "_alias": "org", "name": "Test Org", "slug": "test-org" }],
      "User": [{ "_alias": "admin", "name": "Admin", "email": "admin@test.com", "organizationId": { "_ref": "org" } }],
      "Member": [{ "role": "owner", "organizationId": { "_ref": "org" }, "userId": { "_ref": "admin" } }]
    }
  }

This creates:
1. One Organization (aliased "org")
2. One User (aliased "admin"), with organizationId set explicitly via `_ref`
3. One Member with organizationId and userId set explicitly via `_ref`

The SDK creates them in dependency order (Organization, then User, then Member) because the `_ref` edges say Member depends on both, and User depends on Organization.

### How does the SDK know the create order?

From the `_alias`/`_ref` graph in the payload — nothing else. It does NOT read your ORM's FK graph or relations. A record that another record `_ref`s is created first. A `_ref` to an alias that no record in the SAME payload declares fails with INVALID_BODY ("references unknown alias(es)").

You set every foreign key yourself, including the scope field. Use the exact FK column name from your schema -- whether you called it organizationId, orgId, tenant_fk, or anything else. The value is a `{ "_ref": "..." }` pointing at the parent's `_alias`. The factory for that model owns the actual write.

### Realistic example (org with apps, members)

  {
    "create": {
      "Organization": [{ "_alias": "org", "name": "Acme Corp", "slug": "acme-corp" }],

      "User": [
        { "_alias": "alice", "name": "Alice", "email": "alice@test.com", "organizationId": { "_ref": "org" } },
        { "_alias": "bob", "name": "Bob", "email": "bob@test.com", "organizationId": { "_ref": "org" } }
      ],

      "Member": [
        { "role": "owner", "organizationId": { "_ref": "org" }, "userId": { "_ref": "alice" } },
        { "role": "admin", "organizationId": { "_ref": "org" }, "userId": { "_ref": "bob" } }
      ],

      "Application": [
        {
          "_alias": "webApp",
          "name": "Marketing Website",
          "architecture": "WEB",
          "organizationId": { "_ref": "org" }
        },
        {
          "name": "Android App",
          "architecture": "ANDROID",
          "organizationId": { "_ref": "org" }
        }
      ]
    }
  }

## How the SDK orders records

The SDK has no relation introspection. It builds a dependency graph purely from the `_alias`/`_ref` edges in your payload and topologically sorts it: any record referenced by a `_ref` is created before the record that points at it. Key order in the JSON is irrelevant.

### Setting foreign keys

Every FK is your responsibility, expressed as `{ "_ref": "alias" }`. There is no "FK direction" distinction to reason about — every link, whether it points "up" or "across", is just a `_ref` from the record that holds the FK column to the record it depends on.

Examples:
- Application holds organizationId -> set `"organizationId": { "_ref": "org" }` on each Application record.
- Member holds userId and organizationId -> set both as `_ref`s on each Member record.

This is how you solve the "member-user distribution" problem -- give each User its own `_alias`, then point each Member's userId at the right one. Each member gets its own user, correctly wired.

## What to include in fields

Required: every field marked as required in your schema that does NOT have a default value, is not auto-generated, and is not an auto-updated timestamp.

Unique fields: must have unique values to avoid collisions when tests run in parallel.

  { "name": "Acme Corp", "slug": "acme-corp", "email": "admin@test.com" }

## What to omit

- id -- auto-generated by the database
- Fields with default values -- the database or ORM handles them
- Auto-updated timestamp fields -- handled by the ORM automatically

What you MUST include (the SDK does NOT fill these in):
- Every foreign key -- set it explicitly as `{ "_ref": "alias" }`. The SDK does not wire FKs for you.
- The scope field -- it is a FK like any other. Set it explicitly (usually `{ "_ref": "..." }` to the scope record). The SDK does NOT inject it.

Example: given a model with fields id (auto-generated), name (required), architecture (required enum), organizationId (FK + scope field), createdAt (default now), and updatedAt (auto-updated), you provide name, architecture, and organizationId:

  { "name": "My App", "architecture": "WEB", "organizationId": { "_ref": "org" } }

The SDK handles id, createdAt, and updatedAt. You set organizationId.

## Cross-model references (_alias / _ref)

Every foreign key is a cross-model reference: name the target record with _alias, and point the FK at it with _ref. This is the ONLY way to link records — there is no nesting.

### Example: TestGeneration needs applicationId

TestGeneration has an applicationId pointing at an Application, and Test has a testGenerationId pointing at a TestGeneration. Each model is a top-level key; the FKs are `_ref`s:

  {
    "create": {
      "Application": [{ "_alias": "webApp", "name": "Marketing Website", "architecture": "WEB", "organizationId": { "_ref": "org" } }],

      "TestPlan": [{ "_alias": "smoke", "name": "Smoke Plan", "plan": "content", "applicationId": { "_ref": "webApp" } }],

      "TestGeneration": [{ "_alias": "gen1", "conversation": "[]", "status": "success", "testPlanId": { "_ref": "smoke" }, "applicationId": { "_ref": "webApp" } }],

      "Test": [{ "name": "Homepage Test", "testGenerationId": { "_ref": "gen1" } }],

      "Step": [{ "order": 1, "interaction": "click", "params": {}, "testId": { "_ref": "homepageTest" } }]
    }
  }

Rules:
- _alias is a string name you choose. It must be unique across the entire payload.
- _ref resolves to the id of the aliased record after it's created.
- A _ref to an alias that no record in the SAME payload declares fails with INVALID_BODY ("references unknown alias(es)").
- Key order does not matter — the SDK topologically sorts records from the _alias/_ref graph, so a record is created before anything that _refs it.
- You can chain references: alias a record, then reference it from multiple places.

### Another example: Invitation with inviterId

  {
    "create": {
      "Organization": [{ "_alias": "org", "name": "Org", "slug": "org" }],
      "User": [{ "_alias": "inviter", "name": "Alice", "email": "alice@test.com", "organizationId": { "_ref": "org" } }],
      "Member": [{ "role": "owner", "organizationId": { "_ref": "org" }, "userId": { "_ref": "inviter" } }],
      "Invitation": [
        { "email": "bob@test.com", "organizationId": { "_ref": "org" }, "inviterId": { "_ref": "inviter" }, "role": "admin", "expiresAt": "2025-01-01T00:00:00Z" },
        { "email": "carol@test.com", "organizationId": { "_ref": "org" }, "inviterId": { "_ref": "inviter" }, "role": "member", "expiresAt": "2025-01-01T00:00:00Z" }
      ]
    }
  }

### Another example: TestTag (join table)

  {
    "create": {
      "Tag": [
        { "_alias": "tag1", "name": "Critical", "color": "#FF0000", "organizationId": { "_ref": "org" } },
        { "_alias": "tag2", "name": "High", "color": "#FF8800", "organizationId": { "_ref": "org" } }
      ],
      "Test": [{ "_alias": "test1", "name": "Test", "testGenerationId": { "_ref": "gen1" } }],
      "TestTag": [
        { "testId": { "_ref": "test1" }, "tagId": { "_ref": "tag1" } },
        { "testId": { "_ref": "test1" }, "tagId": { "_ref": "tag2" } }
      ]
    }
  }

## The three standard scenarios

When writing scenarios for a project, create three:

### empty -- Org + user only
Tests empty states, onboarding flows, "no data yet" screens.

  {
    "create": {
      "Organization": [{ "_alias": "org", "name": "Empty Org", "slug": "empty-org" }],
      "User": [{ "_alias": "solo", "name": "Solo User", "email": "solo@test.com", "organizationId": { "_ref": "org" } }],
      "Member": [{ "role": "owner", "organizationId": { "_ref": "org" }, "userId": { "_ref": "solo" } }]
    }
  }

### standard -- Realistic variety
Enough data to test every filter, status, and category. Use descriptive names ("Marketing Website", not "App 1"). Include at least one entity per enum value.

  {
    "create": {
      "Organization": [{ "_alias": "org", "name": "Acme Corp", "slug": "acme-corp" }],
      "User": [
        { "_alias": "alice", "name": "Alice", "email": "alice@test.com", "organizationId": { "_ref": "org" } },
        { "_alias": "bob", "name": "Bob", "email": "bob@test.com", "organizationId": { "_ref": "org" } },
        { "_alias": "carol", "name": "Carol", "email": "carol@test.com", "organizationId": { "_ref": "org" } }
      ],
      "Member": [
        { "role": "owner", "organizationId": { "_ref": "org" }, "userId": { "_ref": "alice" } },
        { "role": "admin", "organizationId": { "_ref": "org" }, "userId": { "_ref": "bob" } },
        { "role": "viewer", "organizationId": { "_ref": "org" }, "userId": { "_ref": "carol" } }
      ],
      "Application": [
        { "_alias": "webApp", "name": "Marketing Website", "architecture": "WEB", "organizationId": { "_ref": "org" } },
        { "name": "Android App", "architecture": "ANDROID", "organizationId": { "_ref": "org" } },
        { "name": "iOS App", "architecture": "IOS", "organizationId": { "_ref": "org" } }
      ],
      "Tag": [
        { "name": "Critical", "color": "#DC2626", "organizationId": { "_ref": "org" } },
        { "name": "P1 - High", "color": "#F97316", "organizationId": { "_ref": "org" } },
        { "name": "Flaky", "color": "#EAB308", "organizationId": { "_ref": "org" } }
      ]
    }
  }

### large -- High volume
Exceeds pagination thresholds. Tests pagination, sort stability, filter performance. Each record is explicitly listed in the array.

  {
    "create": {
      "Organization": [{ "_alias": "org", "name": "Load Test Org", "slug": "load-test" }],
      "User": [{ "_alias": "user", "name": "User", "email": "load@test.com", "organizationId": { "_ref": "org" } }],
      "Member": [{ "role": "owner", "organizationId": { "_ref": "org" }, "userId": { "_ref": "user" } }],
      "Application": [{ "_alias": "app", "name": "App", "architecture": "WEB", "organizationId": { "_ref": "org" } }],
      "Tag": [
        { "name": "Tag 1", "color": "#333", "organizationId": { "_ref": "org" } },
        { "name": "Tag 2", "color": "#333", "organizationId": { "_ref": "org" } },
        { "name": "Tag 3", "color": "#333", "organizationId": { "_ref": "org" } }
      ],
      "TestPlan": [{ "_alias": "plan", "name": "Plan", "plan": "x", "applicationId": { "_ref": "app" } }],
      "TestGeneration": [{ "_alias": "gen1", "conversation": "[]", "testPlanId": { "_ref": "plan" }, "applicationId": { "_ref": "app" } }],
      "Test": [{ "name": "Test", "testGenerationId": { "_ref": "gen1" } }]
    }
  }
