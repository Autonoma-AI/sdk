# Validation

Scenario data is often generated by an LLM. Validation catches mistakes before they hit your production database.

## Database dry-run (checkScenario)

The primary validation method. Runs the full create → teardown cycle against a real database.

The typical workflow: generate a scenario JSON file (by hand or via LLM), then point `checkScenario` at it. The test reads the file, runs it against a real database, and tells you exactly what's wrong.

```typescript
import { readFileSync } from 'node:fs'
import { checkScenario } from '@autonoma-ai/sdk'

// Read the scenario file that was just generated
const scenario = JSON.parse(readFileSync('./scenarios/standard.json', 'utf-8'))

const result = await checkScenario(adapter, scenario)

if (result.valid) {
  console.log('Scenario is valid!')
  console.log(`Create: ${result.timing.upMs}ms, Teardown: ${result.timing.downMs}ms`)
} else {
  console.log(`Failed at phase: ${result.phase}`)
  for (const err of result.errors) {
    console.log(`[${err.phase}] ${err.message}`)
    if (err.fix) console.log(`  Fix: ${err.fix}`)
  }
}
```

For example, if the scenario file has a duplicate slug:

```json
{
  "create": {
    "Organization": [
      { "name": "Org 1", "slug": "same-slug" },
      { "name": "Org 2", "slug": "same-slug" }
    ]
  }
}
```

The result will be:
```
Failed at phase: up
[up] Unique constraint failed on the fields: (`slug`)
  Fix: Unique constraint on (slug). Add {{testRunId}} or {{index}} to make values unique.
```

You fix the JSON file, re-run the test, and repeat until it passes.

### What the result tells you

| Field | Type | Description |
|-------|------|-------------|
| `valid` | boolean | `true` if the full cycle succeeded |
| `phase` | `'ok'` \| `'up'` \| `'down'` | Where it stopped |
| `errors` | array | Each error has `phase`, `message`, and optional `fix` |
| `timing` | `{ upMs, downMs }` | Performance numbers in milliseconds |

| `phase` value | What happened |
|---------------|---------------|
| `ok` | Full create + teardown cycle succeeded |
| `up` | Database rejected the data during creation |
| `down` | Teardown failed (FK constraint during deletion) |

### Common errors and how to fix them

| Error message | What's wrong | How to fix |
|---------------|-------------|-----------|
| `Unique constraint failed on the fields: (\`slug\`)` | Two records have the same value for a unique field | Add `{{testRunId}}` to the field: `"slug": "acme-{{testRunId}}"` |
| `Unique constraint failed on the fields: (\`userId\`,\`organizationId\`)` | A user is a member of the same org twice | Each member must have its own user. Nest each user under its member. |
| `Invalid value for argument \`architecture\`. Expected Architecture.` | Wrong enum value | Check your Prisma schema for valid enum values: `enum Architecture { WEB ANDROID IOS }` |
| `Unknown argument \`applications\`.` | Wrong relation name | Check your Prisma schema for the exact relation field name. It might be `Application` (PascalCase) not `applications`. |
| `Argument \`email\` must not be null.` | A required field is missing from the scenario | Add the field with a value: `"email": "user-{{testRunId}}@test.com"` |
| `Foreign key constraint failed` | A referenced record doesn't exist | Check that parent entities are nested correctly. The parent must exist before the child. |
| `_ref "xyz" not found` | An `_alias` is referenced before it's created | Move the aliased node earlier in the tree (it must appear before any `_ref` to it in depth-first order) |

### Example: fixing a unique constraint

**Broken** — two orgs with the same slug:
```json
{
  "create": {
    "Organization": [
      { "name": "Org 1", "slug": "test-org" },
      { "name": "Org 2", "slug": "test-org" }
    ]
  }
}
```

**Fixed** — unique slugs:
```json
{
  "create": {
    "Organization": [
      { "name": "Org 1", "slug": "test-org-1-{{testRunId}}" },
      { "name": "Org 2", "slug": "test-org-2-{{testRunId}}" }
    ]
  }
}
```

### Example: fixing a wrong relation name

**Broken** — "apps" is not the Prisma relation name:
```json
{
  "Organization": [{
    "apps": [{ "name": "My App" }]
  }]
}
```

**Fixed** — use the exact Prisma relation name:
```prisma
// Your Prisma schema says:
model Organization {
  applications Application[]  // ← the relation name is "applications"
}
```

```json
{
  "Organization": [{
    "applications": [{ "name": "My App" }]
  }]
}
```

### Example: fixing an invalid enum

**Broken** — "DESKTOP" is not a valid enum value:
```json
{ "architecture": "DESKTOP" }
```

**Fixed** — use a valid enum:
```prisma
// Your Prisma schema says:
enum Architecture {
  WEB
  ANDROID
  IOS
}
```

```json
{ "architecture": "WEB" }
```

## Using with testcontainers

The recommended approach for local validation before deploying. Spins up a real Postgres in Docker, runs your scenario files against it, tears down. No test data leaks.

This test is designed as a reusable harness: generate your scenario JSON files (by hand, via LLM, or from the Autonoma platform), drop them in a `scenarios/` folder, and run the test. It reads every `.json` file in the folder and validates each one.

```typescript
// tests/validate-scenarios.test.ts
import { describe, it, expect, beforeAll, afterAll } from 'vitest'
import { PostgreSqlContainer } from '@testcontainers/postgresql'
import { PrismaClient } from '@prisma/client'
import { prismaAdapter } from '@autonoma-ai/sdk-prisma'
import { checkScenario } from '@autonoma-ai/sdk'
import { execSync } from 'node:child_process'
import { readFileSync, readdirSync } from 'node:fs'
import { join } from 'node:path'

// Point this at your scenario files
const SCENARIOS_DIR = join(__dirname, '../scenarios')

describe('scenario validation', () => {
  let container, prisma, adapter

  beforeAll(async () => {
    container = await new PostgreSqlContainer('postgres:16-alpine').start()
    execSync('npx prisma db push --skip-generate --accept-data-loss', {
      env: { ...process.env, DATABASE_URL: container.getConnectionUri() },
      stdio: 'pipe',
    })
    prisma = new PrismaClient({ datasourceUrl: container.getConnectionUri() })
    adapter = prismaAdapter(prisma, { scopeField: 'organizationId' })
  }, 60_000)

  afterAll(async () => {
    await prisma.$disconnect()
    await container.stop()
  })

  // Discover all .json files in the scenarios folder
  const files = readdirSync(SCENARIOS_DIR).filter(f => f.endsWith('.json'))

  for (const file of files) {
    it(`validates ${file}`, async () => {
      const scenario = JSON.parse(readFileSync(join(SCENARIOS_DIR, file), 'utf-8'))
      const result = await checkScenario(adapter, scenario)

      if (!result.valid) {
        for (const err of result.errors) {
          console.log(`[${err.phase}] ${err.message}`)
          if (err.fix) console.log(`  Fix: ${err.fix}`)
        }
      }

      expect(result.valid).toBe(true)
    })
  }
})
```

**Usage**:

1. Generate your scenario files into `scenarios/`:
```
scenarios/
  empty.json       ← org + user only
  standard.json    ← realistic variety
  large.json       ← high volume with _batch
```

2. Run the test:
```bash
npx vitest run tests/validate-scenarios.test.ts
```

3. If a scenario fails, read the error and fix the JSON file. Re-run until all pass.

Later, once deployed, the Autonoma platform validates scenarios against your live endpoint — it calls `up` and `down` directly. But testcontainers lets you catch errors locally before deploying, without risking your staging database.

## Check multiple scenarios at once

```typescript
import { checkAllScenarios } from '@autonoma-ai/sdk'

const results = await checkAllScenarios(adapter, [
  emptyScenario,
  standardScenario,
  largeScenario,
])

for (const result of results) {
  if (!result.valid) {
    console.log(`Failed at ${result.phase}:`, result.errors)
  }
}
```

## The fix loop (for LLM-generated scenarios)

When an LLM generates scenario data, use this loop:

```
1. Run discover to get the schema
2. LLM generates scenario JSON based on the schema
3. Run checkScenario against a real database
4. If errors → read the fix field, edit the scenario, go to step 3
5. Scenario is valid — use it
```

Each error's `fix` field contains actionable instructions. Feed it back to the LLM.
