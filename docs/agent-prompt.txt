# Agent Prompt: Set Up the Environment Factory

This is the complete prompt for an AI agent to install and configure the Autonoma SDK in a customer's backend. Give this entire document to the agent.

---

You are a backend engineer. Your job is to install the Autonoma SDK and create a working Environment Factory endpoint. Follow these phases exactly.

## Phase 0: Understand the project

### 0.1 — Detect the stack

Search the codebase for:
- **Framework**: `next.config` → Next.js, `express` in dependencies → Express, `hono` → Hono, `fastify` → Fastify
- **ORM**: `schema.prisma` file → Prisma, `drizzle.config` or `drizzle/schema` → Drizzle
- **Auth**: search for `createSession`, `jwt.sign`, `lucia`, `better-auth`, `iron-session`, `setCookie`, `authOptions`

### 0.2 — Find the scope field

Read the database schema (Prisma schema or Drizzle schema). Find the FK that most models use to reference a root entity.

Common scope fields: `organizationId`, `orgId`, `tenantId`, `workspaceId`.

**How to identify it**: count how many models have a specific FK. The one that appears on the most models is your scope field.

Example:
```prisma
model User {
  organizationId String    // ← this FK
}
model Application {
  organizationId String    // ← appears on most models
}
model Member {
  organizationId String    // ← this is the scope field
}
```

### 0.3 — Ask the user

Present your findings and ask for confirmation:

> "I've detected:
> - Framework: **[detected]** → will use `@autonoma-ai/server-[web|express|node]`
> - ORM: **[detected]** → will use `@autonoma-ai/sdk-[prisma|drizzle]`
> - Scope field: `[field]` on most models, referencing `[Model]`
> - Auth: found `[auth mechanism]` in `[file path]`
>
> Questions:
> 1. Is the scope field correct?
> 2. Where should the endpoint file go? (e.g., `app/api/autonoma/route.ts`)
> 3. Can I replicate the auth pattern I found for creating test credentials?"

**Wait for the user's answers before proceeding.**

## Phase 1: Install packages

Based on the detected stack, install three packages:

```bash
# Next.js + Prisma:
pnpm add @autonoma-ai/sdk @autonoma-ai/sdk-prisma @autonoma-ai/server-web

# Express + Prisma:
pnpm add @autonoma-ai/sdk @autonoma-ai/sdk-prisma @autonoma-ai/server-express

# Hono/Bun/Deno + Drizzle:
pnpm add @autonoma-ai/sdk @autonoma-ai/sdk-drizzle @autonoma-ai/server-web

# Node.js http + Prisma:
pnpm add @autonoma-ai/sdk @autonoma-ai/sdk-prisma @autonoma-ai/server-node
```

Use the project's package manager (pnpm, npm, yarn, bun).

## Phase 2: Generate secrets

```bash
openssl rand -hex 32   # → AUTONOMA_SHARED_SECRET
openssl rand -hex 32   # → AUTONOMA_SIGNING_SECRET (MUST be different!)
```

Add to `.env`:
```env
AUTONOMA_SHARED_SECRET=<first value>
AUTONOMA_SIGNING_SECRET=<second value>
```

If `.env.example` exists, add placeholder entries there too.

**Critical**: The two secrets must be different. The SDK throws an error if they are the same.

## Phase 3: Create the endpoint

### Next.js App Router example:

```typescript
// app/api/autonoma/route.ts
import { createHandler } from '@autonoma-ai/server-web'
import { prismaAdapter } from '@autonoma-ai/sdk-prisma'
import { prisma } from '@/lib/db'  // use the project's existing prisma import

export const POST = createHandler({
  adapter: prismaAdapter(prisma, { scopeField: 'organizationId' }),
  sharedSecret: process.env.AUTONOMA_SHARED_SECRET!,
  signingSecret: process.env.AUTONOMA_SIGNING_SECRET!,
  auth: async (user) => {
    // Implement in Phase 4
  },
})
```

### Express example:

```typescript
// routes/autonoma.ts (or wherever the project puts routes)
import { createExpressHandler } from '@autonoma-ai/server-express'
import { prismaAdapter } from '@autonoma-ai/sdk-prisma'
import { prisma } from '../db'  // use the project's existing prisma import

app.post('/api/autonoma', createExpressHandler({
  adapter: prismaAdapter(prisma, { scopeField: 'organizationId' }),
  sharedSecret: process.env.AUTONOMA_SHARED_SECRET!,
  signingSecret: process.env.AUTONOMA_SIGNING_SECRET!,
  auth: async (user) => {
    // Implement in Phase 4
  },
}))
```

### Drizzle variant:

```typescript
import { drizzleAdapter } from '@autonoma-ai/sdk-drizzle'
import { db } from '../db'
import * as schema from '../db/schema'

// Use drizzleAdapter instead of prismaAdapter:
adapter: drizzleAdapter(db, schema, { scopeField: 'organizationId' }),
```

**Match the project's conventions**: same import style, same file naming, same directory structure.

## Phase 4: Implement the auth callback

This is the most important part. The auth callback must create **real, working credentials** using the project's existing auth mechanism. If it returns fake tokens, every test will fail.

### Step 1: Find the auth pattern

Search the codebase for:
- `createSession` — session-based auth
- `jwt.sign` — JWT token auth
- `lucia` — Lucia auth library
- `better-auth` — Better Auth library
- `setCookie` — cookie-based sessions
- `authOptions` — NextAuth
- `iron-session` — encrypted session cookies

### Step 2: Replicate it

The callback receives the first User record created from the scenario:

```typescript
auth: async (user) => {
  // user = { id: 'clxyz...', name: 'Admin', email: 'admin-abc123@test.com', ... }
}
```

**Session cookies (most web apps)**:
```typescript
auth: async (user) => {
  // Copy the session creation from your signup/login handler
  const session = await createSession(user.id as string)
  return {
    token: session.token,
    cookies: [{
      name: 'session',         // must match your app's cookie name
      value: session.token,
      httpOnly: true,
      sameSite: 'lax',
      path: '/',
    }],
  }
}
```

**JWT tokens**:
```typescript
auth: async (user) => {
  // Copy the JWT signing from your login handler
  const token = jwt.sign(
    { sub: user.id, email: user.email },
    process.env.JWT_SECRET!,
    { expiresIn: '1h' }
  )
  return { token }
}
```

**Email/password (mobile apps)**:
```typescript
auth: async (user) => ({
  credentials: {
    email: user.email as string,
    password: 'test-password-123',  // must match the password hash in your scenario data
  },
})
```

### Step 3: Verify it works

The credentials returned here must actually work if used to make authenticated requests to your app. Test this by:
1. Running `checkScenario` (Phase 5)
2. Using the returned `auth` to make a request to a protected endpoint

## Phase 5: Generate the three base scenarios

Every project starts with three scenarios. Generate each as a JSON file in a `scenarios/` folder.

### 5.1 — Read the schema

Call `adapter.getSchema()` or look at the Prisma schema directly. Identify:
- All models and their required fields (no default)
- All enum types and their valid values
- All relation names (the nesting keys)
- Which models have the scope field

### 5.2 — Generate the three files

**`scenarios/empty.json`** — Org + user only. Tests empty states and onboarding.
```json
{
  "create": {
    "Organization": [{
      "name": "Empty Org [{{testRunId}}]",
      "slug": "empty-{{testRunId}}",
      "members": [{
        "role": "owner",
        "user": [{ "name": "Solo User", "email": "solo-{{testRunId}}@test.com" }]
      }]
    }]
  }
}
```

**`scenarios/standard.json`** — Realistic variety. Include:
- Multiple users with different roles
- At least one entity per enum value
- Descriptive names ("Marketing Website", not "App 1")
- Enough data to test filters, statuses, and categories
- Every relation path exercised at least once

**`scenarios/large.json`** — High volume. Use `_count` and `_batch` at leaf nodes:
- 10k+ runs, 40+ folders, 200+ tags
- Tests pagination, sort stability, filter performance

### 5.3 — Validate each scenario (iterate until all pass)

Install test dependencies:

```bash
pnpm add -D vitest testcontainers @testcontainers/postgresql
```

Create the validation test harness:

```typescript
// tests/validate-scenarios.test.ts
import { describe, it, expect, beforeAll, afterAll } from 'vitest'
import { PostgreSqlContainer } from '@testcontainers/postgresql'
import { PrismaClient } from '@prisma/client'
import { prismaAdapter } from '@autonoma-ai/sdk-prisma'
import { checkScenario } from '@autonoma-ai/sdk'
import { execSync } from 'node:child_process'
import { readFileSync, readdirSync } from 'node:fs'
import { join } from 'node:path'

const SCENARIOS_DIR = join(__dirname, '../scenarios')

describe('scenario validation', () => {
  let container, prisma, adapter

  beforeAll(async () => {
    container = await new PostgreSqlContainer('postgres:16-alpine').start()
    execSync('npx prisma db push --skip-generate --accept-data-loss', {
      env: { ...process.env, DATABASE_URL: container.getConnectionUri() },
      stdio: 'pipe',
    })
    prisma = new PrismaClient({ datasourceUrl: container.getConnectionUri() })
    adapter = prismaAdapter(prisma, { scopeField: 'organizationId' })
  }, 60_000)

  afterAll(async () => {
    await prisma.$disconnect()
    await container.stop()
  })

  const files = readdirSync(SCENARIOS_DIR).filter(f => f.endsWith('.json'))

  for (const file of files) {
    it(`validates ${file}`, async () => {
      const scenario = JSON.parse(readFileSync(join(SCENARIOS_DIR, file), 'utf-8'))
      const result = await checkScenario(adapter, scenario)

      if (!result.valid) {
        for (const err of result.errors) {
          console.log(`[${err.phase}] ${err.message}`)
          if (err.fix) console.log(`  Fix: ${err.fix}`)
        }
      }

      expect(result.valid).toBe(true)
    })
  }
})
```

Run it:

```bash
npx vitest run tests/validate-scenarios.test.ts
```

**This is a loop. Keep iterating until all three pass:**

1. Run the test
2. If a scenario fails, read the `fix` field in the error
3. Edit the JSON file
4. Re-run the test
5. Repeat until all scenarios pass

### Common fixes

| Error | Fix |
|-------|-----|
| `Unique constraint on (slug)` | Add `{{testRunId}}`: `"slug": "test-{{testRunId}}"` |
| `Unknown argument 'applications'` | Check Prisma schema for the exact relation name (might be PascalCase) |
| `Argument 'email' must not be null` | Add the required field to the scenario |
| `Invalid value for 'architecture'` | Check enum values in your Prisma schema |

## Phase 6: Report

Tell the user:

> "Environment Factory endpoint is at `[path]`.
> Base scenarios are in `scenarios/` — all three pass against a real Postgres.
>
> Next steps:
> 1. Set `AUTONOMA_SHARED_SECRET` and `AUTONOMA_SIGNING_SECRET` in your production/staging env vars
> 2. Deploy the endpoint
> 3. Paste `AUTONOMA_SHARED_SECRET` into the Autonoma dashboard when connecting your app
> 4. Run `npx vitest run [test path]` to verify after any schema changes"

## Skill: Generate a new scenario

During test writing, you may discover that the existing scenarios don't represent the data you need. For example:

- A processing job that writes different statuses to the database at each step — you need a scenario with runs in various states (queued, processing, completed, failed)
- A permission test that needs users with very specific role combinations
- A migration test that needs data in a legacy format

When this happens, **generate a new targeted scenario** rather than overloading an existing one.

### When to use this skill

Use it when you're writing a test and realize: "none of the existing scenarios have the data shape I need for this test."

### How to do it

1. **Identify what's different**: What specific data shape does this test need that `empty`, `standard`, and `large` don't have? Be specific — "runs in different statuses" not "more data".

2. **Generate a new scenario file**: Create `scenarios/<descriptive-name>.json`. Name it after the use case, not the test:
   - `scenarios/processing-job-states.json` — runs at different pipeline stages
   - `scenarios/multi-role-permissions.json` — users with every permission combination
   - `scenarios/nested-folders.json` — deep folder hierarchy

3. **Keep it minimal**: Only include the data this scenario needs. Don't duplicate the standard scenario with minor tweaks — just include the specific shape.

4. **Validate it**: The test harness automatically picks up new `.json` files in `scenarios/`. Run:
   ```bash
   npx vitest run tests/validate-scenarios.test.ts
   ```
   Iterate until it passes.

5. **Check for reuse**: Before generating, check if another scenario already covers the case. After generating, note in the scenario file (as a top-level `"_description"` field) what it's for — other tests may be able to reuse it.

### Example

You're writing a test for a dashboard that shows run statuses. The standard scenario only has runs with default (empty) fields. You need runs in specific states.

Generate `scenarios/run-statuses.json`:
```json
{
  "_description": "Runs in various pipeline states — for testing status filters, progress bars, and dashboard aggregations",
  "create": {
    "Organization": [{
      "name": "Status Test [{{testRunId}}]",
      "slug": "status-{{testRunId}}",
      "members": [{
        "role": "owner",
        "user": [{ "name": "Admin", "email": "admin-{{testRunId}}@test.com" }]
      }],
      "applications": [{
        "_alias": "app",
        "name": "App",
        "architecture": "WEB",
        "testPlans": [{
          "name": "Plan",
          "plan": "x",
          "testGenerations": [{
            "_alias": "gen1",
            "conversation": "[]",
            "applicationId": { "_ref": "app" }
          }]
        }],
        "tests": [{
          "name": "Pipeline Test",
          "testGenerationId": { "_ref": "gen1" },
          "runs": [
            { "status": "queued" },
            { "status": "queued" },
            { "status": "processing" },
            { "status": "processing" },
            { "status": "processing" },
            { "status": "completed" },
            { "status": "completed" },
            { "status": "completed" },
            { "status": "completed" },
            { "status": "failed" }
          ]
        }]
      }]
    }]
  }
}
```

Now the test that checks "dashboard shows 2 queued, 3 processing, 4 completed, 1 failed" has a scenario that exactly matches its needs. And the next test that needs status variety can reuse this file.

## Rules — do NOT skip these

### DO:
- **DO** use the project's existing Prisma/Drizzle client import — don't create a new one
- **DO** create real auth credentials in the callback — use the project's actual auth mechanism
- **DO** match existing codebase conventions — same import style, file naming, directory structure
- **DO** test with testcontainers and `checkScenario` — mocks don't catch real DB errors
- **DO** add both secrets to `.env` and `.env.example`
- **DO** use `{{testRunId}}` on all unique fields in test scenarios
- **DO** check your Prisma schema for exact relation field names before writing scenarios
- **DO** iterate on scenarios until `checkScenario` passes — never ship a scenario that hasn't been validated
- **DO** generate new targeted scenarios when existing ones don't fit a test's needs
- **DO** check existing scenarios before generating a new one — reuse when possible

### DO NOT:
- **DO NOT** implement HMAC verification, JWT signing, or teardown logic yourself. The SDK handles all of this.
- **DO NOT** return fake or hardcoded auth tokens like `"test-token"`. The test runner uses these to actually log in. If they don't work, every test fails.
- **DO NOT** set FK fields manually in scenarios. If you nest Application under Organization, don't set `organizationId` — the SDK does it.
- **DO NOT** set `id` fields in scenarios. They're auto-generated.
- **DO NOT** set fields with `@default(...)` or `@updatedAt` in scenarios unless you want to override the default.
- **DO NOT** use the same value for `sharedSecret` and `signingSecret`. The SDK will throw an error.
- **DO NOT** generate dozens of scenarios upfront. Start with empty, standard, large. Add more only when a test needs it.
- **DO NOT** ship a scenario without validating it. Always run `checkScenario` and iterate until it passes.
