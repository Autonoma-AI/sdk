# Validating scenarios (Rust)

Scenario data is often generated by an LLM, so validate it against a real database before it reaches production. The Rust SDK ships **no** `check_scenario` helper - you validate by driving the real handler through a full `up` then `down` cycle in a `#[tokio::test]`, using your real factories against a test database, and reading the status and body it returns.

## The dry-run path: a tokio test over handle_request

`handle_request(&config, &req)` is the same entry point the server adapters call (`sdks/rust/src/handler.rs:40`). Sign a request with `sign_body`, run `up`, feed the returned `refsToken` into `down`, and assert both succeed. Any failure shows up as a non-200 status and an `error`/`code` body.

```rust
// tests/validate_scenarios.rs
use std::collections::HashMap;
use std::sync::Arc;
use serde_json::{json, Value};
use sqlx::PgPool;
use autonoma_sdk::handler::handle_request;
use autonoma_sdk::hmac::sign_body;
use autonoma_sdk::types::{HandlerConfig, HandlerRequest};
use myapp::autonoma::autonoma_config;   // your real config builder

const SHARED: &str = "test-shared-secret";

fn signed(body: &str) -> HandlerRequest {
    let mut headers = HashMap::new();
    headers.insert("x-signature".into(), sign_body(body, SHARED));
    HandlerRequest { body: body.into(), headers }
}

/// Run one scenario end to end. Returns Ok(()) or the failing phase + body.
async fn run_scenario(config: &HandlerConfig, scenario: &Value) -> Result<(), String> {
    // up
    let up_body = json!({ "action": "up", "create": scenario["create"] }).to_string();
    let up = handle_request(config, &signed(&up_body)).await;
    if up.status != 200 {
        return Err(format!("[up] {}", up.body));
    }
    let token = up.body["refsToken"].as_str().unwrap().to_string();

    // down
    let down_body = json!({ "action": "down", "refsToken": token }).to_string();
    let down = handle_request(config, &signed(&down_body)).await;
    if down.status != 200 {
        return Err(format!("[down] {}", down.body));
    }
    Ok(())
}

#[tokio::test]
async fn validates_all_scenarios() {
    // Point the pool at a real (test) database - your factories run real inserts.
    let pool = Arc::new(PgPool::connect(&std::env::var("DATABASE_URL").unwrap()).await.unwrap());
    let mut config = autonoma_config(pool);
    config.shared_secret = SHARED.into();
    config.signing_secret = "test-signing-secret".into();
    config.allow_production = true;

    for entry in std::fs::read_dir("scenarios").unwrap() {
        let path = entry.unwrap().path();
        if path.extension().and_then(|e| e.to_str()) != Some("json") { continue; }
        let scenario: Value = serde_json::from_str(&std::fs::read_to_string(&path).unwrap()).unwrap();
        if let Err(e) = run_scenario(&config, &scenario).await {
            panic!("{}: {}", path.display(), e);
        }
    }
}
```

Drop each scenario file into a `scenarios/` folder and run:

```bash
# shell
DATABASE_URL=postgres://localhost/myapp_test cargo test --test validate_scenarios
```

`shared_secret` and `signing_secret` must differ or every request fails with `SAME_SECRETS`. Both must match the secret used to sign the request (`SHARED` above).

## Reading a failure

Every failing request returns `{ "error": "...", "code": "..." }` in the body (`sdks/rust/src/errors.rs:21`). The `code` tells you the phase and cause; the `error` message carries the underlying detail.

| Body `code` | Cause | Fix |
|-------------|-------|-----|
| `INVALID_BODY` ("missing required fields ...") | A record omits a `required` field from the factory's `input_fields` | Add the field to the scenario, or mark it optional in `input_fields`. |
| `INVALID_BODY` ("no factory registered for model ...") | A model in `create` has no factory | Register a factory for it and add it to the `FactoryRegistry`. |
| `INVALID_BODY` ("references unknown alias(es)") | A `_ref` targets an alias no record declares | Add the target record with that `_alias`, or fix the name. |
| `FACTORY_MISSING_PK` | A factory's `create` returned a `Map` without an `"id"` key | Insert `"id"` into the returned record. |
| `UNRESOLVED_TOKEN` | A literal `{{...}}` reached the SDK unresolved | Use only `{{testRunId}}`, `{{index}}`, `{{cycle(...)}}`, or a real value. |
| `FACTORY_TEARDOWN_ERROR` | A teardown closure returned `Err` | Fix the delete logic; check FK/reverse order. |
| any error a factory returns from `create` | Your DB rejected the insert (e.g. unique constraint) | The `error` message is your database's - make unique fields distinct across records. |

## The fix loop

Validation is iterative, especially for LLM-generated data:

1. Run `cargo test --test validate_scenarios`.
2. If it fails, read the panic - it prints the file plus the `[phase] {error, code}` body.
3. Edit the scenario JSON and re-run.
4. Repeat until every scenario passes.

## curl alternative

For a one-off check without a test harness, run the same `up`/`down` pair with curl against a running server. See the smoke-test in `implement.md` for how to compute the `x-signature`; send `{"action":"up","create":{...}}`, copy the `refsToken` from the response, then POST `{"action":"down","refsToken":"..."}`. A `200` on both is a pass.
