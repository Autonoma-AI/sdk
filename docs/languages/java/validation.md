# Validating scenarios (Java)

Scenario data is often generated by an LLM, so validate it against a real database before it reaches production. The Java SDK has no dry-run helper - you validate by driving the same handler the platform hits, `AutonomaHandler.handleRequest`, from a JUnit test that runs the full `up` then `down` cycle through your real factories.

## The validation path

`AutonomaHandler.handleRequest(HandlerConfig, HandlerRequest)` is the single entry point the Spring controller calls. In a test you build the same `HandlerConfig` your app uses (real factories, pointed at a test database), sign a request body with `HmacUtil.signBody`, and assert the response status is 200 for both phases.

```java
// src/test/java/com/example/ScenarioValidationTest.java
import ai.autonoma.sdk.AutonomaHandler;
import ai.autonoma.sdk.HmacUtil;
import ai.autonoma.sdk.types.*;
import com.fasterxml.jackson.databind.ObjectMapper;
import org.junit.jupiter.api.Test;

import java.util.Map;

import static org.junit.jupiter.api.Assertions.*;

class ScenarioValidationTest {

  private static final String SHARED = "test-shared-secret";
  private static final String SIGNING = "test-signing-secret";
  private static final ObjectMapper MAPPER = new ObjectMapper();

  private HandlerConfig config() {
    HandlerConfig config = new HandlerConfig(
      "organizationId", SHARED, SIGNING,
      (user, ctx) -> AuthResult.ofHeaders(Map.of("Authorization", "Bearer test"))
    );
    config.setFactories(MyFactories.all());   // real factories, real test DB
    return config;
  }

  private HandlerResponse post(HandlerConfig config, String body) {
    String sig = HmacUtil.signBody(body, SHARED);
    return AutonomaHandler.handleRequest(config, new HandlerRequest(body, Map.of("x-signature", sig)));
  }

  @Test
  void scenarioRoundTrips() throws Exception {
    HandlerConfig config = config();

    // 1. up: create the scenario
    String upBody = """
      {"action":"up","create":{
        "Organization":[{"_alias":"org","name":"Test Org","slug":"test-org"}],
        "User":[{"_alias":"admin","name":"Admin","email":"admin@test.com","organization_id":{"_ref":"org"}}]
      }}
      """;
    HandlerResponse up = post(config, upBody);
    assertEquals(200, up.status(), "up failed: " + up.body());

    // 2. down: tear it back down with the returned refsToken
    String refsToken = (String) up.body().get("refsToken");
    String downBody = MAPPER.writeValueAsString(Map.of("action", "down", "refsToken", refsToken));
    HandlerResponse down = post(config, downBody);
    assertEquals(200, down.status(), "down failed: " + down.body());
  }
}
```

On failure the response `body()` carries `error` and `code` fields (for example `INVALID_BODY`, `FACTORY_MISSING_PK`, `INVALID_REFS_TOKEN`) - read them to see exactly where it broke. A non-200 `up` means creation was rejected; a non-200 `down` means teardown failed.

## Driving every scenario file

Point your factories' database access at a real Postgres (Testcontainers is the reliable way to get one in a test), drop every scenario into a folder as JSON, and loop a parameterized test over all of them.

```java
// src/test/java/com/example/AllScenariosTest.java
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.MethodSource;
import org.testcontainers.containers.PostgreSQLContainer;
```

Add the Testcontainers dependency (`org.testcontainers:postgresql`, test scope) and run with `mvn test`. Start the container and run your schema migrations in a `@BeforeAll` before building the `HandlerConfig`.

## The fix loop

Validation is iterative, especially for LLM-generated data:

1. Run the test.
2. If it fails, read the `code` and `error` in the response `body()`.
3. Edit the scenario JSON and re-run.
4. Repeat until both `up` and `down` return 200.

Common failures and fixes:

| Response signal | Cause | Fix |
|-----------------|-------|-----|
| `FACTORY_MISSING_PK` | A factory's `create` returned a map without `id` | Return at least `{"id": ...}` from every `create`. |
| `INVALID_BODY` - "no factory registered for model X" | A model in `create` has no factory | Register a factory for `X` and add it to the map. |
| `INVALID_BODY` - "Validation failed for model X" | A record does not match the factory's `inputClass` | Add or fix the field; check the `inputClass` declares it (with `@JsonProperty` if the name differs). |
| DB unique-constraint error surfaced in `error` | Two records share a unique value | Make each unique field distinct across records. |
| `INVALID_REFS_TOKEN` on `down` | `up` and `down` used different `signingSecret` | Use one config for both phases. |

## curl as an alternative

If the app is already running against a test database, you can validate over HTTP instead - sign each body with the shared secret and POST it. See Step 9 of `implement.md` for the `discover` smoke test; the same pattern works for `up` and `down` by changing the body.
